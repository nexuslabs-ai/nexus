# Install

Nexus components are copy/own: you paste a component's source into your app and
it is yours from that moment. Nothing installs it, and no upstream change will
ever reach it — editing a pasted component means editing your own file, and
picking up a later fix means pasting the new version over it.

A pasted component still reaches for four things that are not in the file it
came from. Set those up once, in this order, and everything you paste afterwards
works:

1. **Tailwind 4** — the setup the `nx:` prefix depends on.
2. **The token CSS layer** — the tokens and utilities, plus the native
   color-scheme policy.
3. **The appearance provider** — what themes the components and paints before
   hydration.
4. **The `cn` helper** — the module every copied component imports.

The examples target a fresh Next 15 App Router app. Vite wiring lives in
[Theme setup](/getting-started/theme-setup).

## 1. Tailwind 4

```bash
npm install -D tailwindcss @tailwindcss/postcss postcss
```

```js
// postcss.config.mjs
export default {
  plugins: { '@tailwindcss/postcss': {} },
};
```

Do not add an `@import "tailwindcss"` of your own. The Nexus token CSS imports
Tailwind itself, as `@import 'tailwindcss' prefix(nx)` — that prefix is where
`nx:bg-primary-background` comes from. A second, unprefixed import would emit
preflight and the whole utility layer twice.

Tailwind finds class names by scanning your project, so a pasted component's
utilities are generated with no `@source` line: the file sits in your source
tree like any other. `@source` is only for class names automatic detection
cannot reach — `node_modules`, or files outside your project.

## 2. The token CSS layer

Copy the token CSS into your app. Seven files, one entry point:

```
styles/nexus/
├── nexus.css                 # entry — imports Tailwind with prefix(nx), then the six below
├── variables.css             # the --nx-* values, and their .dark overrides
├── typography-utilities.css
├── borderwidth-utilities.css
├── border-color-aliases.css
├── motion-utilities.css
└── spacing-utilities.css
```

Import the entry point from your app's CSS entry point:

```css
/* app/globals.css */
@import '../styles/nexus/nexus.css';
```

That one import is the whole styling surface: the `nx:` utilities, the semantic
color tokens, and the typography, spacing, radius, and motion scales.

Then declare the native color scheme, so the browser themes scrollbars, form
controls, and the page canvas before any JavaScript runs:

```tsx
// app/layout.tsx
import type { Viewport } from 'next';

export const viewport: Viewport = { colorScheme: 'light dark' };
```

Next renders that as `<meta name="color-scheme" content="light dark" />`; outside
Next, write the tag itself. `nexus.css` emits the matching CSS policy — `:root`
advertises both schemes, `:root:not(.dark)` pins light, and `.dark` pins dark —
so native UI follows the app's theme instead of the operating system's.

If you also consume compiled components from the `@nexus_ds/react` package
instead of pasting them, add `@import '@nexus_ds/react/styles.css'` after the
token import. Tailwind does not scan `node_modules`, so the utilities used
inside those components ship as prebuilt CSS.

## 3. The appearance provider

The provider is what turns the token layer into a live theme. It derives the
`--nx-*` values from a single appearance state, toggles `.dark`, and sets the
`data-density` / `data-radius` / `data-shadow` / `data-borderwidth` attributes
the token CSS keys off. Its companion script does that same work inline in
`<head>`, before hydration, so there is no flash of the wrong theme.

The engine behind it is a published package:

```bash
npm install @nexus_ds/core
```

The React wiring is copy/own like the components. Copy the provider in:

```
components/appearance/
├── index.ts      # client surface — NexusAppearanceProvider, useNexusAppearance
├── provider.tsx
├── factory.tsx
├── script.tsx
└── server.ts     # server-safe — NexusAppearanceScript
```

Then wire the script and the provider in the root layout:

```tsx
// app/layout.tsx
import type { Viewport } from 'next';
import { DEFAULT_NEXUS_APPEARANCE } from '@nexus_ds/core';

import { NexusAppearanceProvider } from '@/components/appearance';
import { NexusAppearanceScript } from '@/components/appearance/server';

import './globals.css';

export const viewport: Viewport = { colorScheme: 'light dark' };

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en" suppressHydrationWarning>
      <head>
        <NexusAppearanceScript
          storageKey="app-appearance"
          defaultState={DEFAULT_NEXUS_APPEARANCE}
        />
      </head>
      <body className="nx:bg-background nx:text-foreground">
        <NexusAppearanceProvider
          storageKey="app-appearance"
          defaultState={DEFAULT_NEXUS_APPEARANCE}
        >
          {children}
        </NexusAppearanceProvider>
      </body>
    </html>
  );
}
```

Both need the same `storageKey`: the provider persists the user's choice there,
and the script restores it on the next load. Change what the app opens with by
overriding fields on the default state — spread it and set `mode` to `'dark'` to
open dark, or `brandColor` and `surfaceTone` to move the palette.

[Theme setup](/getting-started/theme-setup) covers the rest: cookie-seeded SSR,
Vite's `transformIndexHtml`, and the storage policies. Its snippets import from
`@nexus_ds/react/appearance`, which is these same modules under their package
name.

## 4. The `cn` helper

Every Nexus component composes its classes through `cn`, so this file has to
exist before the first paste:

```bash
npm install clsx tailwind-merge
```

Copy `lib/utils.ts` in. It is `clsx` wrapped in a `tailwind-merge` instance
configured with `prefix: 'nx'` and the Nexus custom utility groups. That
configuration is what lets `<Button className="nx:bg-error-background" />`
override the variant's own background instead of landing beside it in the class
list and losing to source order.

## Paste a component

Setup is done. `Button` pulls in three more files from the same source tree:

```
components/ui/button.tsx
components/ui/spinner.tsx             # the loading state
components/ui/button-group-context.ts # size inherited from a ButtonGroup
lib/icons.ts                          # the internal @tabler/icons-react barrel
```

and the packages those files import:

```bash
npm install @radix-ui/react-slot class-variance-authority @tabler/icons-react
```

Point the relative imports at wherever you put the files, then render it:

```tsx
import { Button } from '@/components/ui/button';

<Button>Primary</Button>
<Button variant="secondary">Secondary</Button>
<Button variant="outline">Outline</Button>
<Button variant="ghost">Ghost</Button>
```

<div className="nx:flex nx:flex-wrap nx:gap-3 nx:my-6">
  <Button>Primary</Button>
  <Button variant="secondary">Secondary</Button>
  <Button variant="outline">Outline</Button>
  <Button variant="ghost">Ghost</Button>
</div>

Unstyled buttons mean the token import from step 2 never reached the page.
Styled buttons that stay light when you switch to dark mean the provider from
step 3 is not wrapping them.
