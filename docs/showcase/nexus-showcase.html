Nexus Design System · @nexus_ds

One token engine.
Every framework.

Nexus is not a component library with a theme bolted on. It is a framework-agnostic token engine — six independent theming axes derived from a single state object, namespaced so it drops into a product that already has its own CSS — that today ships a React binding. The components are the engine's first consumer, not the product.

01 — The case

What actually goes wrong without this

Six failure modes. Each one maps to a specific architectural decision later in the page — the system is a response to this list, not a greenfield aesthetic exercise.

A
Adopting a component library means rewriting your CSS config
The library ships unprefixed classes, so its class names and theme keys have to live in your Tailwind config, next to the ones your product already uses. This is the single most common reason a team evaluates a design system and walks away — the migration is not "add a button," it is "reconcile two token vocabularies across an existing app." → Namespace isolation
B
Theming lives inside the component library
Contrast rules, hover shades, and dark-mode logic get written into React components. The day you need Vue, Svelte, or React Native, you re-implement all of it — and then maintain two systems that quietly disagree. → Portability
C
Dark mode is a second theme, maintained by hand
Two lists of hex values, edited independently. One is always stale. Nexus treats this as the root cause: two producers of the same tokens will drift, and no amount of reconciliation testing prevents it — it only detects it late. → Architecture
D
Everything except color is hard-coded
Most systems make color themeable and then bake spacing, radius, shadow depth, and stroke weight into components as literals. So "make this product feel denser" or "we need square corners for this brand" becomes a refactor instead of a setting. → The five other axes
E
Contrast is checked by eye, at review time
"Looks fine to me" is the accessibility gate. Nobody re-checks the other 80 token pairs after a palette tweak, and nobody checks them at all in the four surface tones the team does not personally use. → The APCA gate
F
Copy-own solves ownership, then forks the token layer
shadcn/ui's copy-into-your-repo model is right about component ownership. But when four apps each own their copy of the CSS variables, four themes diverge and no upgrade path exists. Nexus keeps components copy-own and pulls the token layer back into a versioned engine. → vs shadcn
02 — Architecture

One brain, two invocation times

deriveTheme() is the only thing in the system that produces a semantic token value. It runs once at build time to bake a static floor into CSS, and again at runtime whenever appearance state changes. Same function, same inputs, same output.

The load-bearing line is the CSS variable fallback. It is what lets a single set of generated utilities serve both a fully static build and a live-themed runtime, with no rebuild and no duplicate stylesheet. 

/* packages/tailwind/nexus.css — generated */
@theme inline {
  --color-container: var(--nx-color-container, oklch(1 0 0));
}
/*  --color-*     the Tailwind v4 key that generates nx:bg-container
    --nx-color-*  the runtime override the appearance provider injects
    the fallback  the build-time floor: correct with JavaScript disabled  */

Three source layers feed it, in strict dependency order: primitives (--nx-*, DTCG JSON, context-independent raw values) → semantic (roles, engine-produced) → utilities (nx:-prefixed Tailwind classes). A component that reaches past the semantic layer to a primitive fails lint.

03 — Adoption

Nothing Nexus emits can collide with your app

This is the practical adoption argument, and in our experience the one that decides evaluations. A design system you cannot install next to your existing CSS is a design system you do not install.

The blocker, concretely

shadcn/ui components are written with unprefixed utilities — bg-background, text-muted-foreground, rounded-lg. Those classes only mean anything if your Tailwind config defines them. So adopting shadcn is not "add a component"; it is merging another vocabulary into the config your product already runs on. If your app already defines background, primary, or muted to mean something else, that is a migration before you render a single button.

Unprefixed — needs your config

<!-- resolves against the HOST's Tailwind theme -->
<button class="bg-background text-foreground
  border-input rounded-lg px-4 h-10">

// your tailwind.config must now define
// background, foreground, input, and a
// radius scale — alongside whatever your
// product already called those things.

Namespaced — needs nothing

<!-- resolves only against Nexus's own theme -->
<button class="nx:bg-container nx:text-foreground
  nx:border-border-default nx:rounded-base
  nx:px-3 nx:h-10">

// your tailwind.config is untouched.
// your existing .bg-container, if you have
// one, is a different class entirely.

What is namespaced, surface by surface

SurfaceNexus emitsCollision risk
Utility classes nx:bg-container, nx:p-container, nx:typography-label-default None — nx: is on every class the library writes
Primitive variables --nx-radius-md, --nx-spacing-4, --nx-motion-duration-fast None — all 484 carry the --nx- namespace
Tailwind theme keys --nx-color-*, --nx-z-index-* None — prefix(nx) rewrites every emitted key
Runtime overrides --nx-color-background, injected by the provider None — same namespace, owned by the engine
Tailwind's stock scales Nothing — deleted with --color-*: initial None — Nexus never emits bg-blue-500 to fight yours
Component styles Prebuilt CSS (@nexus_ds/react/styles.css) None — your Tailwind never scans or compiles Nexus source
Read-surface aliases :root { --color-background: … } The one shared name space — see the note below

That last row is deliberate and worth saying out loud rather than glossing: the generated CSS also publishes an unprefixed :root { --color-* } alias block so a consumer's own stylesheet can read Nexus tokens directly. It is the single unprefixed surface in the package. If the host app also defines Tailwind v4 --color-* theme keys, those names overlap and load order decides — worth a look during integration. Every class remains fully isolated regardless.

The prefix is also load-bearing for the copy-own model. Because Tailwind does not scan node_modules, the utilities used inside compiled Nexus components ship as prebuilt CSS. Two imports and the system is live — no config merge, no content-glob edits, no theme reconciliation. 

/* the entire integration surface */
@import '@nexus_ds/tailwind';      /* the nx: token utilities */
@import '@nexus_ds/react/styles.css';  /* styles for the compiled components */

The prefix ordering rule

nx: comes before every modifier — nx:hover:bg-container-hover, nx:md:flex, nx:[&>svg]:size-4. Never hover:nx:…. This is not a style preference; the wrong order silently produces a class that does nothing, so a custom ESLint rule fails the build on it.

Re-pointing a layer from outside

Because the utilities read prefixed variables, a consumer can re-point a whole layer from their own stylesheet without touching component source: 

/* loaded after Nexus */
:root { --nx-z-index-sticky: 35; }
04 — Axis one of six

Color, derived rather than authored

Color gets the most machinery because it is the axis where hand-maintenance fails fastest. Three mechanisms, then a proof.

The APCA gate — the part that makes it trustworthy

Nexus uses APCA (the perceptual contrast model behind the WCAG 3 drafts) rather than WCAG 2.x ratios, which misjudge exactly the mid-lightness pairs a token system produces constantly. Three tiers: body Lc ≥ 75 for fluent reading, ui Lc ≥ 60 for labels and controls, incidental Lc ≥ 45 for muted text and focus rings. Muted inks are walked to the quietest value that still clears their floor on their specific surface — not set to a fixed grey and hoped over.

50 token pairs are declared as an explicit contract — this ink on that surface, at this tier. CI sweeps them across 6 brand seeds × 5 surface tones × 3 contrast settings = 90 derived themes. That is 4,500 contrast assertions on every run, and the build fails if one drops below its floor. No combination a consumer can select produces an illegible pair, and that property is re-proved on every commit.

05 — Axes two through six

Everything else is themeable too

This is where most systems stop. Nexus treats spacing rhythm, corner radius, shadow depth, stroke weight, type scale, and motion as first-class theming axes — each with its own named scales, all shipped in the stylesheet at once and swapped by a data attribute on any ancestor. First paint, without the flash

A runtime-themed system has one classic failure: the default theme paints, then the user's theme replaces it. Nexus closes that window with a snapshot written before the first frame — theme CSS, preference CSS, the .dark class, all four data attributes, and native color-scheme, before React exists. 

// server: read the cookie, build the snapshot, inline it in <head>
const snapshot = createNexusAppearanceSnapshotFromCookie(
  cookieStore.get(DEFAULT_COOKIE_KEY)?.value,
  defaultAppearance,
);

Precedence, stated once

The cookie seeds the server render. After hydration, localStorage is the client source of truth and wins. The cookie is written from client state for the next request — it is never read during hydration. That one rule is what keeps SSR output stable.

Versioned and sanitized

Snapshots carry SNAPSHOT_VERSION (currently 5), so a stale persisted snapshot is rejected rather than trusted. Every field passes through sanitizeNexusAppearance — including a rejection filter on font-family strings, since those are interpolated into a live <style> rule.

07 — Layout model

Components adapt to their container, not the viewport

A second set of decisions that has nothing to do with color, and that a consuming team inherits for free.

@container over breakpoints
Component-internal responsive behaviour queries the parent's width, so a card renders correctly whether it lands in a hero or a sidebar. Viewport prefixes are reserved for page-shell decisions and full-viewport overlays — a documented exception, since a Dialog's trigger is genuinely its position in the viewport.
rem breakpoints track text size
Breakpoints are 40 / 48 / 64 / 80 / 96rem. Because they are rem-based they respond to the browser's default font size — a user who enlarges type gets a roomier layout tier automatically. That is accessibility behaviour, not a unit preference.
Declarative visibility
<Show above="lg"> and <Hide containerBelow="md"> replace hand-toggled hidden classes. They swap display: contents ↔ none, so children never unmount and an inline or grid child keeps its natural layout. A discriminated union rejects passing two axes at compile time.
A published sizing contract
Heights, inline padding, and width behaviour are a table in the rules, not per-component improvisation. A new component adds a row before it changes sizing.
~44px touch-target floor
A hit-area floor, not a visual-size mandate. Dense controls keep their compact box and extend the tappable area with a coarse-pointer overlay — nx:pointer-coarse:after:-inset-1.5 — so desktop stays tight and touch stays usable.
container-type has a cost policy
container-type is only declared where a child actually issues an @container query. Each declaration makes the browser track that element's size; applying it by habit reintroduces exactly the cost the property was designed to let you avoid.

A six-token stacking scale

Shadow communicates perceived elevation; z-index controls actual paint order. Nexus keeps them as independent axes and gives stacking its own semantic scale.

08 — The bet

One token system, many frameworks

Everything above was built so that adding Vue, Svelte, Angular, or React Native is a binding — not a second design system.

Why the engine ports

@nexus_ds/core imports no framework and touches no DOM. It is a pure function from state to values. Two exported calls are the entire port surface: 

deriveTheme(contract: ThemeDerivationInput) → { light: TokenMap, dark: TokenMap }
themeToCss(derived: DerivedTheme)          → string   // :root { … } :root.dark { … }

A host that owns its own styling calls deriveTheme and reads the token map directly — no CSS involved. This is the documented path for Electron shells, native wrappers, and React Native, and it is why the engine ships to npm while the components are copy-own. 

// a non-React shell, from the @nexus_ds/core README
const state    = { ...DEFAULT_NEXUS_APPEARANCE, brandColor: '#2563eb', surfaceTone: 'slate' };
const snapshot = createNexusAppearanceSnapshotFromState(state);
const paint    = resolveFirstPaint(snapshot, false);

document.documentElement.classList.toggle('dark', paint.className === 'dark');
themeStyle.textContent = themeToCss(deriveTheme(createNexusThemeContract(snapshot.state)));

What a new framework inherits vs. what it builds

The line to hold in a conversation: a second framework does not get a second theme. It imports the same npm package, calls the same function, and gets byte-identical token values — so a React app and a Vue app in the same product render the same grey, provably, without anyone coordinating.

Honest status

  • Shipped: the engine (@nexus_ds/core, on npm) and the React binding — 63 components.
  • Designed for, not yet built: Vue, Svelte, Angular, and React Native bindings. The engine has no framework coupling to remove first, which is the part that is usually expensive.
  • Native platforms: tokens are already DTCG, so Swift / Kotlin outputs are a Style Dictionary target rather than a re-authoring exercise. The runtime derivation would need a port to be live on native; the generated value sets travel today.
  • In flight: the copy-own export tool that vendors components and theme CSS into a consuming app (tracked as issue #541).
09 — Comparison

How this differs from shadcn/ui

Nexus adopts shadcn's best idea — you own the component source — and rejects its token model. Every divergence below is written down in shadcn-divergences.md and enforced by lint, so adaptation is mechanical rather than a matter of taste.

Concernshadcn/uiNexusWhy
Install cost Its theme keys must join your Tailwind config Two CSS imports; your config is untouched The adoption blocker, removed
Class namespace bg-background nx:bg-container Vendored code cannot collide with the host's classes
Who produces tokens You do — hand-authored CSS variables per app A versioned engine, one producer Four apps stop meaning four themes
Themeable axes Color, plus a radius variable Six — color, density, corners, elevation, stroke, motion "Make it denser" is a setting, not a refactor
Token naming bg-primary nx:bg-primary-background A family is not a value; the suffix names the role
Hover / active hover:bg-primary/90 nx:hover:bg-primary-background-hover An opacity guess is not a theme decision
Disabled states Opacity on the element nx:bg-primary-disabled Opacity compounds unpredictably over a tinted surface
The accent token bg-accent Removed — mapped per surface "Accent" meant three different hovers; now it names which surface
Status colors destructive only error, success, warning, information — 44 tokens Products need four states, not one
Contrast checking Author's responsibility 4,500 APCA assertions in CI The property is proved, not asserted
Escape hatch bg-blue-500 available Deleted via --color-*: initial The convention is compiled in, not remembered
Convention enforcement Docs and review Four custom ESLint rules + eight audits A contributor who never read the rules still cannot break them

What Nexus keeps from shadcn

  • Copy-own components. You get the source, you can edit it, there is no black box to fight.
  • Radix underneath. Accessibility semantics, focus management, and portal behaviour come from primitives.
  • CVA for variants. The variant-to-class map stays a readable table.
  • The asChild pattern. Composition over a polymorphic as prop.

Where shadcn is the better choice

  • One app, one framework, one theme. A derivation engine is overhead you will not recover.
  • You want the ecosystem. Blocks, registries, and community components target shadcn's token names.
  • Time-to-first-screen. npx shadcn add button is minutes; Nexus asks you to adopt a token discipline first.

Nexus pays off where you have multiple products, multiple frameworks, an existing app with its own CSS, or a brand that must be re-themeable per tenant.

10 — Components

The component contract

63 components, all the same shape. That regularity is what makes the library portable — a Vue binding re-implements rendering, not decisions.

data-slot / data-variant / data-size
The stable test and styling surface. Tests never assert on class names, because nx: classes change when variants are restyled. Attributes are part of the contract; classes are an implementation detail.
CVA for enums, ternaries for booleans
Variant and size go in the cva() table. loading and disabled stay explicit in the component body, so boolean logic never hides inside a class map.
One focus treatment, system-wide
Every keyboard-focusable control uses the same focus-default ring — no per-variant focus color, no destructive swap. Focus is a system signal ("you are here"), not a status.
Menu rows get a tint, not a ring
Radix roving focus moves DOM focus on pointer hover, so a ring would flash for mouse users. Overlay rows use a surface tint instead. The rule is written down as a surface exception map, not decided per component.
Composition over render props
No renderItem, no cardComponent, no mode discriminator gating different render branches. Use children or split into per-mode components — enforced by lint, not by review.
Structural hooks vs. identity hooks
A wrapper may rename data-slot, so internal CSS keys off a separate attribute the component owns. It is the kind of detail that only shows up once a component is wrapped — and it is specified rather than discovered. 
const buttonVariants = cva(
  'nx:inline-flex nx:rounded-base nx:border-default
   nx:transition-[color,background-color,border-color,scale]
   nx:active:scale-[0.96] nx:motion-reduce:active:scale-100
   nx:focus-visible:outline-2 nx:focus-visible:outline-focus-default
   nx:focus-visible:outline-offset-(--focus-offset)',
  { variants: {
      variant: {
        default: 'nx:bg-primary-background nx:text-primary-foreground
                  nx:hover:bg-primary-background-hover
                  nx:active:bg-primary-background-active
                  nx:disabled:bg-primary-disabled',
        /* destructive, outline, dashed, secondary, ghost, link, error */
      },
      size: { sm: 'nx:h-8 nx:px-2.5', default: 'nx:h-10 nx:px-3', lg: 'nx:h-12 nx:px-3.5',
              'icon-sm': 'nx:size-8', icon: 'nx:size-10', 'icon-lg': 'nx:size-12' },
  }});

Four things to point at: every class carries the namespace; hover / active / disabled are tokens, not opacity; the press animation has an explicit motion-reduce counterpart; and the focus offset is itself tokenised, so the focus treatment retunes system-wide from one variable.

11 — Enforcement

Conventions that fail the build

A design system is only as good as what it prevents on a Friday afternoon. Nexus converts its written rules into checks — so a contributor who has never read them still cannot violate them.

Lint ruleCatches
nx-class-conventionsWrong prefix order (hover:nx:…), the banned accent token, incomplete token paths, raw primitives like nx:bg-blue-500
no-render-prop-typesProps typed as (…) => ReactNode or ComponentType — composition via children instead of injected renderers
no-multi-statement-jsx-handlerInline JSX handlers with 3+ statements or a nested callback object — extract and name them
canonical-spacing-stepsA px value in a spacing mode file that is off the canonical step set

Stories are the tests

There are no *.test.tsx files for components — the config explicitly excludes them. A single *.stories.tsx does four jobs: visual documentation, an interactive prop playground, behaviour assertions via play functions in real Chromium, and an axe-core accessibility pass that fails the run on any violation. 70 story files across 63 components.

The audit surface

audit:contrast
The 4,500-assertion APCA sweep across every seed, tone, and contrast setting.
audit:class-refs
Every nx: class in component source resolves to a real registry token.
audit:colorblind
Categorical chart colors stay distinguishable under simulated color-vision deficiency.
audit:mode-distinctness
Two appearance modes that emit identical values are a bug — a mode nobody can see is dead config.
audit:browser-support
New platform features are checked against the floor: Chrome 111, Edge 111, Firefox 113, Safari 15.4, Samsung 22.
audit:runtime-exports
The published engine's public surface is an allowlist — accidental exports fail CI.
validate:spacing-modes
Every density mode defines the same role keys, so no mode can silently drop one.
size-limit
Hard budgets: 95 kB for the ESM bundle, 30 kB CSS, 45 kB for the appearance entry.

All of it runs behind one command. make verify is the pre-push gate and is exactly what CI runs: lint, format check, typecheck, the full test suite, then the token, accessibility, and browser audits.

12 — Cheat sheet

Five things to say out loud

If the room only remembers five sentences, these are the ones that carry the argument.

The frame
"Nexus is a token engine that happens to ship React components — not a component library that happens to have tokens."
Adoption
"Every class is nx:-prefixed and every variable is --nx--namespaced, so it drops into a product that already has its own CSS. With shadcn you have to merge its vocabulary into your Tailwind config first — that's where most evaluations die."
Scope
"Six theming axes, not one. Color, density, corners, elevation, stroke, motion — all swappable at runtime by a data attribute, no rebuild."
The proof
"No combination of brand color, surface tone, and contrast setting a consumer can pick will produce an illegible pair — 4,500 APCA assertions re-prove that on every commit."
The payoff
"Adding Vue or Svelte means writing a binding, not a design system. The engine has zero framework coupling, so a React app and a Vue app render provably identical tokens."

And the honest caveat, if someone asks: React is the only binding shipped today, and the copy-own export tool is still landing. The claim is that the expensive part — decoupling theming from the framework — is already done.
